# HandyNest — дополнение к ТЗ: запуск в Узбекистане, позиционирование и защита сделки

Версия: 1.0  
Дата: 2026-06-13  
Статус: дополнение к актуальному ТЗ `HandyNest_TZ_for_Codex_ru_v6.md`  
Назначение: зафиксировать изменения после решения запускать платформу сначала в Узбекистане, а не в Казахстане.

---

## 1. Главное изменение стратегии

Первый рынок запуска проекта меняется:

```text
Было в старом ТЗ / ранней версии стратегии:
Казахстан как первый рынок запуска.

Стало:
Узбекистан как первый рынок запуска.
Первый город для MVP: Ташкент.
```

Это дополнение не отменяет всю архитектуру старого ТЗ, но меняет рыночный фокус, локализацию, конкурентное позиционирование, UX-приоритеты и правила работы с контактами.

## 2. Новый рыночный фокус

### 2.1. Первый рынок

```text
Country: Uzbekistan
Initial city: Tashkent
Initial language priority: Russian + Uzbek Latin
Initial launch mode: city-first, category-limited MVP
```

### 2.2. Почему Узбекистан выбран первым

Узбекистан выбран как первый рынок, потому что:

```text
- рынок больше по населению, чем Казахстан;
- есть спрос на бытовые услуги и мастеров;
- уже есть конкуренты, значит спрос подтверждён;
- основной найденный конкурент Ustabor больше похож на каталог мастеров и контактов;
- есть возможность отличиться моделью controlled / transactional marketplace;
- запускать нужно не всю страну сразу, а Ташкент + 3–5 категорий.
```

## 3. Конкурентное позиционирование

### 3.1. Важное уточнение

Нельзя считать, что в Узбекистане нет конкурентов.

В Узбекистане уже есть сервисы поиска мастеров, например Ustabor. Поэтому проект должен позиционироваться не как ещё один каталог мастеров, а как платформа безопасного выполнения задачи.

```text
Ustabor = найти мастера / получить контакт / договориться напрямую.
HandyNest / новый бренд = создать задачу / получить отклики / выбрать исполнителя / вести сделку внутри платформы / завершить работу / оставить отзыв / открыть спор при проблеме.
```

### 3.2. Главное отличие проекта

Проект не должен быть обычной доской объявлений или каталогом специалистов.

Главное отличие:

```text
Не просто найти контакт мастера,
а довести задачу до результата внутри платформы.
```

Целевой lifecycle остаётся ключевой частью продукта:

```text
Task -> TaskOffer -> Accepted Offer -> Deal -> Chat -> Work Submission -> Acceptance / Revision / Dispute -> Feedback
```

## 4. Первый MVP для Узбекистана

### 4.1. География

Для MVP не запускать сразу весь Узбекистан.

```text
MVP city: Tashkent
Later expansion: Samarkand, Bukhara, Namangan, Andijan and other cities after validation.
```

### 4.2. Первые категории

Для MVP выбрать 3–5 категорий, где понятная боль и высокий спрос:

```text
1. Сантехник
2. Электрик
3. Ремонт стиральных машин / бытовой техники
4. Клининг
5. Грузчики / мелкие перевозки
```

Не запускать сразу 80+ категорий. Это создаст перегрузку интерфейса, усложнит модерацию и размоет позиционирование.

### 4.3. Режим запуска

На старте допускается ручная операционная поддержка:

```text
- ручная проверка первых исполнителей;
- ручное сопровождение первых сделок;
- ручная модерация жалоб и спорных ситуаций;
- ручной сбор обратной связи от заказчиков и исполнителей.
```

## 5. Название и бренд

Рабочее название `HandyNest` остаётся внутренним техническим названием до выбора финального бренда.

Для рынка Узбекистана нужно выбрать короткое, понятное и запоминающееся название.

### 5.1. Не использовать названия вокруг `Usta`

После обнаружения конкурента Ustabor не рекомендуется использовать названия:

```text
Usta
Ustam
TopUsta
UstaGo
TezUsta
```

Причины:

```text
- высокая вероятность путаницы с Ustabor;
- слабая уникальность бренда;
- риск выглядеть как копия существующего сервиса;
- сложнее продвигать бренд отдельно.
```

### 5.2. Предпочтительные направления нейминга

Лучше рассматривать короткие названия без `Usta`, например:

```text
Bajar
Qil
Topar
Bormi
Ishla
```

Финальное название нужно проверить отдельно:

```text
- домен .uz;
- Telegram username;
- Instagram;
- Google Play / App Store;
- товарный знак;
- звучание для носителей узбекского языка;
- отсутствие сильной похожести на конкурентов.
```

## 6. Модель контактов и защита от обхода платформы

### 6.1. Важное бизнес-правило

Платформа не должна строиться только на запрете контактов.

Полностью запретить обход невозможно. Пользователи могут принять отклик, обменяться контактами, отменить сделку и выполнить работу напрямую.

Цель платформы:

```text
- сделать обход менее удобным;
- сделать сделку внутри платформы более выгодной и безопасной;
- видеть подозрительные паттерны;
- ограничивать систематический обход;
- давать пользователю ценность, которую он теряет при уходе из платформы.
```

### 6.2. Контакты до принятия отклика

До принятия отклика:

```text
- телефоны, email, Telegram, WhatsApp, Instagram и другие внешние контакты запрещены;
- система должна проверять сообщения и описание задачи на попытки обмена контактами;
- подозрительные сообщения блокируются, маскируются или отправляются на модерацию;
- повторные нарушения повышают risk score пользователя.
```

### 6.3. Контакты после принятия отклика

После принятия отклика:

```text
- создаётся Deal;
- создаётся Chat;
- основной канал общения остаётся внутри платформы;
- телефон не должен открываться автоматически;
- контакт открывается только через явное действие пользователя.
```

Пример UI-действия:

```text
Открыть номер для связи
```

Контакт может быть открыт только если:

```text
- сделка активна;
- исполнитель выбран;
- категория требует офлайн-координации;
- пользователь имеет право видеть контакт;
- действие логируется.
```

### 6.4. Контакты для офлайн-услуг

Для офлайн-услуг нельзя навсегда скрывать телефон. В реальности мастер может нуждаться в звонке:

```text
- не может найти подъезд;
- нужно уточнить время прибытия;
- у заказчика плохой интернет;
- нужно быстро согласовать бытовую деталь.
```

Поэтому правило не “контакты никогда не видны”, а:

```text
Контакты скрыты до создания сделки.
После создания сделки контакт может быть открыт контролируемо, явно и с логированием.
```

## 7. ContactReveal: новая сущность

Добавить сущность `ContactReveal`.

Назначение: фиксировать факт контролируемого открытия контакта между участниками сделки.

Пример полей:

```text
ContactReveal
- id
- dealId
- taskId
- revealedByUserId
- revealedToUserId
- contactOwnerUserId
- contactType: PHONE / EMAIL / MESSENGER / OTHER
- revealReason
- categoryId
- createdAt
- ipAddress
- userAgent
```

Правила:

```text
- ContactReveal создаётся только после активной сделки, если категория разрешает открытие контакта.
- Любое открытие контакта должно попадать в AuditLog.
- Открытие контакта не должно автоматически завершать или отменять сделку.
- Отмена сделки после открытия контакта считается антифрод-сигналом.
```

## 8. Антифрод-события и risk score

### 8.1. Обязательные события

Добавить или явно использовать события:

```text
OFFER_ACCEPTED
DEAL_CREATED
CHAT_CREATED
CONTACT_REVEALED
DEAL_CANCELED
DEAL_COMPLETED
DISPUTE_OPENED
REVISION_REQUESTED
WORK_SUBMITTED
FEEDBACK_CREATED
```

Эти события должны попадать в audit/risk pipeline.

### 8.2. Подозрительные паттерны

Подозрительными считаются ситуации:

```text
- контакт открыт, затем сделка быстро отменена;
- пользователь часто принимает отклик и отменяет после открытия контакта;
- исполнитель часто получает открытие контакта, но сделки редко завершаются;
- заказчик часто открывает контакты разных исполнителей и отменяет сделки;
- в чате есть попытки обмена контактами до разрешённого этапа;
- пользователь часто выбирает причину отмены “другая причина” после открытия контакта;
- повторяющиеся пары заказчик-исполнитель часто отменяют сделки после контакта.
```

### 8.3. Пример risk rules

```text
IF CONTACT_REVEALED AND DEAL_CANCELED within 2 hours THEN risk +1
IF user has 3 such cases in 7 days THEN manual review
IF performer has many contact reveals but low completion rate THEN reduce visibility / manual review
IF customer repeatedly accepts offers and cancels after contact reveal THEN warning / temporary restriction
```

Важно: эти правила не должны автоматически банить пользователя без контекста. На MVP лучше использовать предупреждения и ручную проверку.

## 9. Причины отмены сделки

Отмена сделки должна требовать причину.

Пример enum:

```text
DealCancelReason
- CUSTOMER_CHANGED_MIND
- PERFORMER_NOT_RESPONDING
- CUSTOMER_NOT_RESPONDING
- PRICE_NOT_ACCEPTED
- SCHEDULE_NOT_ACCEPTED
- TASK_NO_LONGER_ACTUAL
- WRONG_PERFORMER_SELECTED
- SAFETY_CONCERN
- DUPLICATE_TASK
- OTHER
```

Правила:

```text
- Если контакт был открыт, причина отмены обязательна.
- Частое использование OTHER после открытия контакта повышает risk score.
- Для SAFETY_CONCERN можно предлагать открыть жалобу.
- Отмена после CONTACT_REVEALED должна сохраняться как отдельный аналитический признак.
```

---

## 10. Антифрод в чате

До разрешённого этапа система должна находить попытки обмена контактами.

Проверять:

```text
- номера телефонов;
- email;
- Telegram username;
- WhatsApp / Instagram / Facebook / TikTok username;
- фразы: “напиши в телеграм”, “скинь номер”, “позвони”, “номер на фото”;
- цифры через пробелы;
- цифры словами;
- замены символов: sobaka, точка, тг, tg, wa;
- контакты на изображениях в будущем через OCR/AI-модерацию.
```

MVP-подход:

```text
1. Сначала deterministic rules / regex.
2. AI-модерация только для подозрительных или сложных случаев.
3. Не блокировать нормальную коммуникацию после создания сделки, если contact reveal разрешён.
```

---

## 11. Ценность сделки внутри платформы

Чтобы пользователи не уходили напрямую, платформа должна давать понятную ценность:

```text
- история договорённостей;
- чат как доказательство;
- фото и файлы по задаче;
- статус выполнения;
- кнопка “Работа выполнена”;
- кнопки “Принять”, “Попросить доработку”, “Открыть спор”;
- отзыв только после завершённой сделки;
- рейтинг исполнителя на основе завершённых сделок;
- жалобы и модерация;
- повторный заказ;
- избранные исполнители;
- будущая возможность защиты оплаты.
```

В интерфейсе нужно объяснять это коротко:

```text
Работайте внутри платформы — так сохраняется история сделки и можно открыть спор при проблеме.
```

Не использовать длинные юридические тексты в основном пользовательском flow.

## 12. Монетизация и обход

На MVP не вводить агрессивную комиссию, потому что это усилит мотивацию обходить платформу.

Рекомендуемый MVP-подход:

```text
- заказчик бесплатно;
- исполнитель получает ограниченное число бесплатных откликов;
- мягкие лимиты для новых исполнителей;
- платное продвижение позже;
- Pro-профиль позже;
- success fee только после появления on-platform payment;
- escrow не делать в первой версии.
```

Ограничение бесплатных откликов помогает снизить массовый сбор контактов.

## 13. UX/UI для Узбекистана: простота и понятность

### 13.1. Главный принцип UI

Интерфейс должен быть максимально простым, mobile-first и не перегруженным текстом.

Причина: часть целевой аудитории может быть не очень уверенной в использовании сложных интернет-сервисов. Поэтому пользователь должен сразу понимать:

```text
- что это за сервис;
- что нужно нажать;
- как создать заявку;
- как выбрать исполнителя;
- что происходит дальше.
```

Не использовать формулировки, которые звучат пренебрежительно к пользователям. В документации и продукте использовать нейтральную формулировку:

```text
часть аудитории может иметь низкий digital experience;
поэтому интерфейс должен быть простым, визуальным и пошаговым.
```

### 13.2. UI не должен быть перегружен

Запрещено перегружать интерфейс:

```text
- длинными текстовыми блоками;
- большим количеством кнопок на одном экране;
- сложными фильтрами на первом шаге;
- юридическими объяснениями в пользовательском flow;
- большим количеством категорий на главной;
- техническими терминами типа “transactional marketplace”, “deal lifecycle”, “verification level”.
```

### 13.3. Новый пользователь должен сразу видеть главный action

На главном экране должны быть 1–2 главных действия:

```text
Найти мастера
Стать исполнителем
```

Для MVP можно сделать основной акцент:

```text
Опишите задачу — мастера сами предложат цену и время.
```

### 13.4. Создание задачи должно быть пошаговым

Форма создания задачи должна быть простой:

```text
1. Что нужно сделать?
2. Где нужно выполнить?
3. Когда удобно?
4. Добавьте фото, если есть.
5. Укажите бюджет, если знаете.
```

Каждый шаг должен быть коротким. Не показывать все поля сразу, если это перегружает экран.

### 13.5. Использовать визуальные подсказки

Использовать:

```text
- крупные кнопки;
- простые иконки;
- короткие подписи;
- примеры задач;
- подсказки в input placeholder;
- прогресс шагов;
- понятные статусы сделки.
```

Примеры коротких placeholder:

```text
Например: течёт кран на кухне
Например: не включается стиральная машина
Например: нужна уборка 2-комнатной квартиры
```

### 13.6. Статусы должны быть человеческими

Не показывать пользователю технические enum-status.

Примеры:

```text
OPEN -> Ждём отклики мастеров
IN_PROGRESS -> Работа в процессе
WORK_SUBMITTED -> Мастер отметил работу выполненной
REVISION_REQUESTED -> Заказчик попросил доработку
COMPLETED -> Работа завершена
DISPUTED -> Открыт спор
CANCELED -> Сделка отменена
```

### 13.7. Минимум текста, максимум понятного действия

В каждом важном состоянии показывать:

```text
- что произошло;
- что пользователь может сделать сейчас;
- одну главную кнопку;
- одну вторичную кнопку максимум.
```

Пример:

```text
Мастер отметил работу выполненной.
Проверьте результат.

[Принять работу]
[Попросить доработку]
[Открыть спор]
```

Если три кнопки выглядят перегруженно, использовать визуальную иерархию:

```text
Primary: Принять работу
Secondary: Попросить доработку
Danger/link: Открыть спор
```

### 13.8. Языки UI

Для MVP:

```text
- русский;
- узбекский латиницей.
```

Английский можно отложить.

Все тексты должны быть подготовлены через i18n, без хардкода строк в компонентах.

## 14. Изменения для backend/domain

Добавить или проверить наличие:

```text
- ContactReveal entity;
- ContactRevealRepository;
- ContactRevealService;
- ContactRevealController или endpoint внутри Deal/Chat модуля;
- ContactType enum;
- DealCancelReason enum;
- RiskEvent rules for contact reveal + cancellation;
- audit events for contact reveal;
- permissions for contact reveal;
- category-level flag: allowsContactReveal;
- category-level flag: requiresOnsiteCoordination.
```

### 14.1. Category flags

В `Category` добавить или предусмотреть:

```text
allowsContactReveal: boolean
requiresOnsiteCoordination: boolean
contactRevealStage: AFTER_DEAL_CREATED / AFTER_WORK_STARTED / NEVER
```

Для MVP можно упростить:

```text
allowsContactReveal boolean
```

Но future-ready лучше хранить stage.

### 14.2. Access control

Право открыть контакт есть только у участников сделки:

```text
- customer of deal;
- performer of deal;
- admin/moderator for support purposes.
```

Нельзя открывать контакты:

```text
- до принятия отклика;
- по чужой сделке;
- по отменённой или истёкшей сделке, если нет специальных правил;
- если категория запрещает contact reveal.
```

## 15. Изменения для frontend

Frontend должен учитывать:

```text
- короткий и простой onboarding;
- отдельный action “Открыть номер для связи”;
- объяснение пользы сделки внутри платформы;
- простую форму создания задачи;
- минимум текста на экранах;
- mobile-first layout;
- RU + Uzbek Latin i18n;
- человеческие статусы вместо enum;
- понятные empty states;
- подсказки для новых пользователей.
```

### 15.1. Главный экран MVP

Не делать сложный маркетинговый лендинг на первом экране.

Минимально:

```text
Заголовок: Найдите мастера в Ташкенте
Подзаголовок: Опишите задачу — исполнители предложат цену и время
Primary button: Создать заявку
Secondary button: Стать исполнителем
```

### 15.2. Экран создания задачи

Не показывать 20 категорий и длинную форму сразу.

Лучший UX:

```text
- поле “Что нужно сделать?”;
- AI/category suggestion после ввода;
- простые популярные категории плитками;
- фото как optional;
- город/район;
- время;
- бюджет optional.
```

## 16. Изменения для Codex / разработки

Если backend уже начал разрабатываться под Казахстан, не переписывать всё сразу.

Codex должен сделать миграцию по фазам:

```text
Phase 1: Обновить документацию и конфигурацию рынка по умолчанию.
Phase 2: Добавить Country/Region/City/District seed для Uzbekistan/Tashkent.
Phase 3: Проверить, что geo-слой не захардкожен под Kazakhstan.
Phase 4: Добавить ContactReveal и DealCancelReason.
Phase 5: Добавить audit/risk events для contact reveal и cancellation.
Phase 6: Обновить frontend copy и UX под простой Uzbekistan-first MVP.
```

### 16.1. Нельзя делать

Codex не должен:

```text
- удалять поддержку Казахстана из архитектуры;
- хардкодить Узбекистан во всех местах;
- ломать существующую country/geo-модель;
- переписывать весь проект одним большим PR;
- добавлять escrow/payment в MVP без отдельного решения;
- делать перегруженный UI с длинными текстами.
```

### 16.2. Нужно сделать

Codex должен:

```text
- оставить multi-country архитектуру;
- выставить Uzbekistan как default launch country;
- добавить Tashkent как initial city;
- подготовить RU + Uzbek Latin тексты;
- добавить contact reveal control;
- добавить risk signals для обхода платформы;
- упростить UI для новых пользователей.
```

## 17. Короткое резюме для команды/Codex

```text
Проект меняет первый рынок запуска с Казахстана на Узбекистан.
Первый город: Ташкент.
Проект не должен копировать Ustabor как каталог мастеров.
Главная модель: task -> offer -> deal -> chat -> submit -> accept/revision/dispute -> feedback.
Контакты скрыты до сделки.
После создания сделки контакт можно открыть только контролируемо, явно и с логированием.
Отмена сделки после открытия контакта является антифрод-сигналом.
UI должен быть максимально простым, mobile-first, без перегруза текстом, с понятными кнопками для новых пользователей.
Архитектура остаётся multi-country; Узбекистан становится default launch market, а не единственной страной навсегда.
```
