# Техническое задание для Codex: HandyNest — маркетплейс услуг для Казахстана

Версия: 6.0, с синхронизированными entity, roadmap, testing и production-ready требованиями

## 0. Назначение документа

Этот документ является основным техническим заданием для разработки платформы **HandyNest** в Codex.

HandyNest — онлайн-платформа, которая соединяет заказчиков, нуждающихся в услугах, с исполнителями, готовыми эти услуги выполнить. Платформа должна работать как современная альтернатива YouDo, Profi, Kabanchik, Work-Zilla и Freelancehunt, но с более удобным UX, прозрачной сделкой, встроенным чатом, безопасностью, отзывами и возможностью масштабирования.

Первый рынок запуска: **Казахстан, по всей стране**.

MVP должен поддерживать две модели услуг:

1. **Локальные оффлайн-услуги**: ремонт, уборка, доставка, бытовая помощь, мастера, переезды, клининг, услуги на месте.
2. **Удалённые digital-услуги**: дизайн, разработка, тексты, маркетинг, консультации, онлайн-помощь, небольшие digital-задачи.

## 1. Главные продуктовые решения

### 1.1. Первый рынок

Первый рынок: **Казахстан**.

Поддерживаемые города в MVP:

- Алматы;
- Астана;
- Шымкент;
- Караганда;
- Актобе;
- Тараз;
- Павлодар;
- Усть-Каменогорск;
- Семей;
- Костанай;
- Кызылорда;
- Уральск;
- Атырау;
- Актау;
- Туркестан;
- остальные города Казахстана через справочник.

На уровне БД и API нельзя жёстко зашивать только один город. Нужно сразу проектировать поддержку страны, региона и города.

### 1.2. Языки интерфейса

MVP должен быть готов к мультиязычности:

- русский — основной язык MVP;
- казахский — обязательная подготовка архитектуры i18n;
- английский — опционально для будущего.

Backend должен возвращать коды ошибок и системные значения так, чтобы frontend мог переводить их через словари.

### 1.3. Тип платформы

Платформа должна быть **transactional marketplace**, а не просто доской объявлений.

Главная цепочка:

```text
Заказ → Отклики → Выбор исполнителя → Чат сделки → Выполнение → Приёмка → Отзыв → Рейтинг
```

Для части категорий может быть оплата без эскроу, но архитектура должна поддерживать будущую защищённую оплату.

### 1.4. Главная UX-идея

Пользователь не должен думать о сложных статусах. Для него интерфейс должен быть простым:

Для заказчика:

```text
Создать заказ → Получить отклики → Выбрать исполнителя → Общаться в чате → Принять работу → Оставить отзыв
```

Для исполнителя:

```text
Найти заказ → Откликнуться → Быть выбранным → Выполнить → Отправить на проверку → Получить отзыв/оплату
```

## 2. Целевой стек

### 2.1. Backend

Использовать:

- Java 21;
- Spring Boot 3.5.x;
- Maven 3.9.x;
- Spring Web MVC;
- Spring Security;
- JWT access token;
- Refresh token;
- Spring Data JPA;
- Hibernate;
- PostgreSQL;
- Liquibase;
- MinIO как S3-compatible object storage для локальной/dev-среды;
- S3-compatible storage abstraction для production;
- MapStruct;
- Lombok;
- Bean Validation;
- SpringDoc OpenAPI;
- Docker;
- Docker Compose;
- JUnit 5;
- Mockito;
- Testcontainers;
- Spring Security Test;
- JaCoCo.

### 2.2. Почему REST API

Платформа должна быть backend-first REST API, потому что в будущем нужны:

- веб-приложение;
- мобильное приложение;
- админ-панель;
- интеграции с платежами;
- push-уведомления;
- внешние сервисы проверки документов.

Не использовать Thymeleaf/HTMX для этой платформы как основной UI.

### 2.3. Что не использовать в MVP

Не использовать в MVP:

- микросервисы;
- Kafka;
- RabbitMQ;
- Elasticsearch;
- Redis как обязательную зависимость;
- собственный платёжный кошелёк;
- сложную recommendation system;
- AI-модерацию как обязательную функцию;
- WebSocket как обязательную первую реализацию.

Но архитектура должна позволять добавить эти возможности позже.

---

### 2.4. Хранилище файлов

Файлы должны храниться не в PostgreSQL, а в object storage.

Для локальной разработки и Docker Compose использовать:

```text
MinIO
```

Для production использовать абстракцию S3-compatible storage:

```text
FileStorageService
S3FileStorageService
MinioFileStorageService
LocalFileStorageService только для тестов
```

MVP-правило:

- локально/dev: MinIO;
- test: Testcontainers MinIO или mock FileStorageService;
- production: S3-compatible storage, выбранный владельцем продукта.

Физически сохранять в storage:

- фотографии заказа;
- вложения в чате;
- результаты работ;
- доказательства по спору;
- документы для верификации;
- аватары;
- портфолио.

В БД хранить только метаданные файла:

```text
storageKey
bucket
originalFilename
contentType
sizeBytes
checksum
visibility
ownerId
createdAt
```

Документы верификации должны храниться в отдельном bucket/prefix с ограниченным доступом. Публичные URL для документов верификации запрещены.

### 3.3. Правила кода

Codex обязан соблюдать:

- не писать бизнес-логику в контроллерах;
- контроллеры принимают запросы, валидируют DTO и вызывают сервисы;
- бизнес-логика находится в сервисах;
- доступ к БД только через repositories;
- наружу не отдавать JPA Entity;
- все публичные ответы API возвращать через DTO;
- Entity/DTO маппить через MapStruct;
- не использовать `@Data` на JPA Entity;
- использовать `BigDecimal` для денег;
- использовать `Instant` для дат и времени;
- все изменения БД делать через Liquibase;
- не хранить секреты в коде;
- не использовать `.anyRequest().permitAll()` в SecurityConfig;
- не добавлять лишние зависимости без причины;
- после каждого этапа проект должен компилироваться.

## 4. Роли пользователей

### 4.1. Guest

Неавторизованный пользователь.

Может:

- смотреть публичные категории;
- смотреть часть публичных заказов без контактных данных;
- зарегистрироваться;
- войти в систему.

Не может:

- создавать заказы;
- отправлять отклики;
- писать в чат;
- видеть контакты;
- видеть приватные данные исполнителей.

### 4.2. Customer

Заказчик.

Может:

- создавать заказы;
- редактировать свои заказы до выбора исполнителя;
- отменять свои открытые заказы;
- получать отклики;
- выбирать исполнителя;
- общаться в чате сделки;
- просить доработку;
- принимать работу;
- открывать спор;
- оставлять отзыв;
- делать повторный заказ тому же исполнителю.

### 4.3. Performer

Исполнитель.

Исполнитель — это пользователь с профилем исполнителя.

Может:

- создать профиль исполнителя;
- выбрать категории услуг;
- указать город, радиус выезда, формат работы;
- проходить верификацию;
- искать заказы;
- отправлять отклики;
- общаться в чате после выбора;
- отправлять работу на проверку;
- получать отзывы;
- отвечать на отзывы, если это разрешено;
- получать статус Top Performer после ручной проверки.

### 4.4. Admin

Администратор.

Может:

- управлять пользователями;
- блокировать пользователей;
- управлять категориями;
- модерировать заказы;
- проверять исполнителей;
- рассматривать жалобы;
- рассматривать споры;
- управлять справочниками;
- просматривать audit log;
- настраивать рискованные категории.

### 4.5. Moderator

Опциональная роль для будущего.

Может:

- проверять заказы;
- проверять жалобы;
- проверять документы;
- помогать в спорах.

## 5. Модель открытия контактов

### 5.1. Проблема

Если открыть телефон или WhatsApp сразу, пользователи уйдут с платформы, и бизнес потеряет:

- контроль качества;
- отзывы;
- монетизацию;
- безопасность;
- возможность решить спор.

Если слишком сильно закрыть контакты, пользователям будет неудобно, особенно в локальных оффлайн-услугах.

### 5.2. Лучшее решение для MVP

Использовать гибридную модель:

```text
До выбора исполнителя → прямые контакты скрыты
После выбора исполнителя → открывается защищённый чат внутри платформы
После резерва оплаты или подтверждения сделки → можно открыть телефон, если категория требует звонка
```

### 5.3. Правила

До выбора исполнителя:

- заказчик видит отклики;
- заказчик видит рейтинг, профиль, отзывы, бейджи;
- заказчик не видит телефон/email исполнителя;
- исполнитель не видит телефон/email заказчика;
- сообщения возможны только в ограниченном формате, если нужен уточняющий вопрос.

После выбора исполнителя:

- создаётся чат сделки;
- стороны могут писать в чате;
- прямые контакты всё ещё скрыты по умолчанию;
- платформа предупреждает не переходить в сторонние мессенджеры до подтверждения условий.

После подтверждения сделки:

- для оффлайн-заказов можно открыть телефон;
- для digital-заказов телефон обычно не нужен;
- открытие контакта логируется.

### 5.4. Категории, где телефон можно открыть раньше

Телефон можно открыть после выбора исполнителя, но до оплаты, если категория требует срочной координации:

- аварийный сантехник;
- электрик;
- вскрытие замков, если категория разрешена;
- срочная доставка;
- переезд;
- курьер;
- выездной мастер.

Но даже в этих случаях чат сделки должен остаться главным местом фиксации условий.

### 5.5. Антифрод

Backend должен уметь обнаруживать в сообщениях:

- номера телефонов;
- email;
- ссылки;
- Telegram/WhatsApp/Instagram;
- попытки оплаты вне платформы;
- подозрительные фразы.

На MVP не блокировать всё жёстко, но:

- показывать предупреждение;
- сохранять risk event;
- при повторениях ограничивать аккаунт;
- давать администратору список подозрительных чатов.

## 6. Приёмка работы из чата

### 6.1. Лучшее решение

Не делать только одну кнопку «Принять работу».

Нужно сделать 3 сценария:

```text
Принять работу
Попросить доработку
Открыть спор
```

### 6.2. Почему так

Одна кнопка слишком слабая для реальной платформы. Если работа плохая, заказчику нужен понятный вариант, иначе он уйдёт в поддержку или просто не завершит заказ.

### 6.3. Flow

Исполнитель нажимает в чате:

```text
Отправить работу на проверку
```

Backend:

- переводит заказ в `WORK_SUBMITTED`;
- создаёт системное сообщение в чате;
- показывает заказчику action panel.

Заказчик видит в чате:

```text
Работа отправлена на проверку

[Принять работу]
[Попросить доработку]
[Открыть спор]
```

### 6.4. Принять работу

При нажатии:

- заказ переходит в `COMPLETED`;
- фиксируется `completedAt`;
- чат закрывается для новых условий, но остаётся доступным для чтения;
- если есть on-platform payment, запускается выплата;
- открывается возможность оставить отзыв.

### 6.5. Попросить доработку

Заказчик обязан указать причину.

Backend:

- переводит заказ обратно в `IN_PROGRESS`;
- создаёт системное сообщение;
- увеличивает счётчик доработок;
- сохраняет текст причины.

Ограничение:

- максимум 2 запроса доработки без спора;
- после 3-й попытки система предлагает открыть спор.

### 6.6. Открыть спор

Заказчик или исполнитель может открыть спор.

Backend:

- переводит заказ в `DISPUTED`;
- создаёт `DisputeCase`;
- блокирует завершение сделки до решения;
- уведомляет администратора.

## 7. Milestones / этапы работ

### 7.1. Решение

В MVP milestones нужны, но не для всех заказов.

Использовать правило:

```text
Обычные недорогие заказы → без этапов
Дорогие или сложные заказы → можно включить этапы
```

### 7.2. Когда предлагать этапы

Этапы предлагать, если:

- цена выше заданного порога;
- срок больше 3 дней;
- digital-заказ требует нескольких результатов;
- заказчик сам включил этапы;
- категория помечена как сложная.

Для Казахстана в MVP можно заложить конфиг:

```text
milestone_threshold = 100000 KZT
```

Значение должно быть в настройках, не хардкодить.

### 7.3. Примеры категорий с milestones

- разработка сайта;
- дизайн-проект;
- ремонт квартиры;
- крупный переезд;
- юридическая подготовка документов;
- маркетинговая кампания.

### 7.4. Entity Milestone

Каноническое описание сущности `Milestone` находится в разделе **16.15**.

Важное правило: milestone привязан к `dealId`, потому что этапы согласуются уже после выбора исполнителя и создания сделки. `taskId` можно хранить как денормализованную ссылку для быстрых запросов и аналитики, но главным владельцем milestone является `Deal`.

MVP может реализовать milestones без частичного платежа, но структура должна быть готова к будущему частичному escrow.

## 8. Верификация исполнителей

### 8.1. Лучшее решение

Использовать ступенчатую верификацию.

Не требовать максимум документов у всех сразу. Это отпугнёт исполнителей.

### 8.2. Уровни верификации

#### Level 0 — Basic

Требуется:

- email;
- телефон;
- пароль;
- город;
- имя.

Может:

- создать профиль;
- смотреть заказы;
- заполнить портфолио.

Не может:

- брать рискованные категории;
- получать бейдж Verified;
- попадать в Top Performers.

#### Level 1 — Phone Verified

Требуется:

- подтверждённый телефон через SMS/OTP.

Может:

- откликаться на низкорисковые заказы;
- выполнять digital-заказы малого бюджета.

#### Level 2 — ID Verified

Требуется:

- удостоверение личности / паспорт;
- ИИН, если применимо;
- selfie/liveness через провайдера или ручную проверку;
- согласие на обработку персональных данных.

Может:

- брать большинство оффлайн-заказов;
- получать бейдж «Документы проверены»;
- получать больше доверия в поиске.

#### Level 3 — Payment Verified

Требуется:

- привязанная карта или банковский счёт;
- проверка владельца платёжного метода через PSP.

Может:

- получать выплаты;
- работать с on-platform payments;
- участвовать в защищённых сделках.

#### Level 4 — Business Verified

Требуется:

- ИП/самозанятый/компания;
- реквизиты;
- налоговые данные;
- документы компании.

Может:

- работать с корпоративными заказчиками;
- получать крупные заказы;
- участвовать в B2B-сделках.

### 8.3. MVP-решение

В MVP обязательно реализовать:

- Level 0;
- Level 1;
- Level 2 как ручную проверку через админку;
- Level 3 как подготовку под PSP;
- Level 4 как future-ready структуру.

### 8.4. Проверка документов

В MVP можно реализовать ручную проверку:

- исполнитель загружает документ;
- администратор видит заявку;
- администратор approve/reject;
- причина отказа сохраняется;
- все действия логируются.

Файлы документов должны храниться отдельно от публичных вложений, доступ только для админов с правами.

## 9. Корпоративные заказчики

### 9.1. Решение

В MVP не делать полноценный B2B-документооборот, но заложить структуру.

### 9.2. Почему

Корпоративные заказчики полезны для роста, но если делать счета, акты, реквизиты и бухгалтерию сразу, MVP станет слишком тяжёлым.

### 9.3. В MVP сделать

Добавить тип аккаунта:

```text
PERSONAL
BUSINESS
```

Для `BUSINESS` хранить:

- companyName;
- bin;
- legalAddress;
- contactPerson;
- billingEmail;
- verificationStatus.

Но:

- не генерировать счета автоматически;
- не делать закрывающие документы;
- не делать сложную бухгалтерию.

### 9.4. В будущей версии

Добавить:

- счета;
- акты;
- договоры;

## 10. Категории и модерация

### 10.1. Главный принцип каталога

Каталог категорий нельзя переносить в платформу один в один из огромного списка. Для MVP нужен **широкий, но управляемый каталог**: достаточно категорий для спроса, но без перегруза UI, юридических рисков и сложной модерации.

Категория в HandyNest — это не просто название. От категории должны зависеть бизнес-правила:

- какой уровень верификации нужен исполнителю;
- можно ли открыть контакты;
- можно ли платить вне платформы;
- можно ли использовать эскроу;
- нужны ли milestones;
- нужна ли ручная модерация;
- можно ли показывать категорию публично;
- можно ли прикреплять файлы;
- можно ли выполнять услугу удалённо;
- нужен ли адрес и геолокация;
- разрешена ли категория в MVP.

Главное правило для Codex: **не загружать весь исходный список категорий в базу как есть**. Нужно использовать очищенное дерево MVP и дать администратору возможность расширять каталог позже.

### 10.2. Поля Category

Сущность `Category` должна содержать технические и бизнес-поля. Локализованные названия и описания хранятся отдельно в `CategoryTranslation`.

Поля `Category`:

- id;
- parentId;
- slug;
- icon;
- riskLevel;
- serviceMode;
- launchPhase;
- active;
- publicVisible;
- sortOrder;
- requiresVerificationLevel;
- requiresManualApproval;
- requiresLicense;
- allowsRemote;
- allowsOnsite;
- allowsEscrow;
- allowsCash;
- allowsMilestones;
- allowsAttachments;
- allowsContactReveal;
- createdAt;
- updatedAt.

Поля `CategoryTranslation`:

- id;
- categoryId;
- locale;
- name;
- description;
- createdAt;
- updatedAt.

### 10.3. Enum: CategoryRiskLevel

```text
LOW
MEDIUM
HIGH
PROHIBITED
```

Описание:

- `LOW` — низкий риск, можно запускать в MVP без ручной проверки каждого заказа;
- `MEDIUM` — есть риск ущерба, нужен минимум phone verification, иногда ID verification;
- `HIGH` — повышенный риск, нужен ID verification, ручные правила, иногда лицензии;
- `PROHIBITED` — запрещено для публикации или запрещено в MVP.

### 10.4. Enum: CategoryLaunchPhase

```text
MVP
PHASE_2
PHASE_3
PROHIBITED_FOR_MVP
PROHIBITED_ALWAYS
```

### 10.12. Требования к админке категорий

Администратор должен иметь возможность:

- редактировать категорию;

- менять riskLevel;
- менять required verification level;
- включать/выключать ручную модерацию;
- включать/выключать возможность эскроу;
- включать/выключать возможность оплаты вне платформы;
- включать/выключать milestones;
- менять порядок сортировки;
- добавлять синонимы для поиска;
- добавлять локализованные названия на русском и казахском.

### 10.13. Требования к поиску по категориям

Категории должны поддерживать:

- поиск по названию;
- поиск по синонимам;
- поиск по slug;
- фильтр по городу;
- фильтр по remote/onsite;
- фильтр по riskLevel для админа;
- скрытие запрещённых и неактивных категорий от обычных пользователей.

### 10.14. Итоговое правило для MVP

Для MVP:

```text
Оставить: примерно 18 главных категорий
Сократить подкатегории: до 5–10 на категорию
Рискованные услуги: скрыть или включать только после проверки
Запрещённые услуги: убрать полностью
Дубли: объединить
Слишком мелкие бренды/типы: перенести в поля формы заказа
```

## 11. Unit economics и монетизация

### 11.1. Лучшее решение

Использовать гибридную модель, чтобы не отпугнуть пользователей.

MVP не должен быть агрессивно платным.

### 11.2. Модель MVP

#### Для заказчика

Бесплатно:

- регистрация;
- создание заказа;
- получение откликов;
- выбор исполнителя;
- чат;
- отзыв.

Платно позже:

- срочное продвижение заказа;
- выделение заказа;
- премиум-подбор исполнителя;
- корпоративные функции;
- защищённая сделка, если комиссию платит заказчик.

#### Для исполнителя

Бесплатно:

- регистрация;
- создание профиля;
- первые отклики в месяц;
- просмотр заказов;
- получение отзывов.

Платно позже:

- дополнительные отклики;
- продвижение профиля;
- PRO-подписка;
- доступ к премиум-заказам;
- success fee с выполненного заказа через платформу.

### 11.3. Рекомендуемая модель

Для запуска:

```text
Freemium + мягкий lead limit + success fee только для on-platform payment
```

Пример:

- 10 бесплатных откликов в месяц для новых исполнителей;
- дальше отклики списывают внутренние credits;
- credits можно купить или получить за хороший рейтинг;
- если заказ оплачен через платформу — комиссия 5–10%;
- если заказ без эскроу — платформа может брать только lead fee или ничего на старте;
- Top Performers могут платить подписку за продвижение.

### 11.4. Не делать в MVP

Не вводить сразу жёсткую плату за каждый отклик.

Это может убить рост на старте, особенно в Казахстане, где нужно сначала создать доверие и ликвидность рынка.

### 11.5. Future monetization

Добавить позже:

- Pro-профиль;
- платное продвижение;
- подписка для исполнителей;
- комиссия с безопасной сделки;
- комиссия с B2B-заказов;
- подписка для корпоративных заказчиков;
- insurance/protection fee;
- premium support.

## 14. Rebooking / повторный заказ

### 14.1. Решение

Rebooking нужен в MVP.

### 14.2. Почему

Это один из лучших способов увеличить retention.

Если заказчику понравился исполнитель, он должен легко заказать его снова.

### 14.3. MVP-функции

Добавить:

- кнопка «Заказать снова»;
- кнопка «Написать исполнителю по новому заказу»;
- создание нового заказа на основе предыдущего;
- связь `repeatOfTaskId`;
- список избранных исполнителей.

### 14.4. Ограничение

Нельзя позволять бесконечно переписываться вне контекста заказа без создания новой сделки.

Новый заказ должен создавать новый chat/deal.

## 15. Top Performers / managed marketplace

### 15.1. Решение

Да, нужен отдельный режим Top Performers, но не как обязательная часть для всех.

### 15.2. Почему

Это позволит платформе быстро создать доверие.

### 15.3. MVP

Добавить бейдж:

```text
Top Performer
```

Условия:

- ID verified;
- phone verified;
- минимум N завершённых заказов;
- рейтинг выше заданного порога;
- нет серьёзных жалоб;
- ручная проверка администратором.

### 15.4. Привилегии

Top Performer получает:

- выше позицию в выдаче;
- бейдж доверия;
- доступ к премиум-заказам;
- возможность быть рекомендованным платформой;
- меньше ограничений по откликам.

### 15.5. Admin

Админ может:

- назначить Top Performer;
- снять статус;
- указать причину;
- видеть историю изменений.

## 18. Security

### 18.1. Spring Security

Открытые endpoints:

```text
/api/v1/auth/register
/api/v1/auth/login
/api/v1/auth/refresh
/api/v1/categories
/api/v1/categories/**
/api/v1/tasks
/api/v1/tasks/{publicId}
/v3/api-docs/**
/swagger-ui/**
/actuator/health
```

Все остальные endpoints требуют авторизации.

Важно: публичные `GET /api/v1/tasks` и `GET /api/v1/tasks/{publicId}` должны возвращать только публичные опубликованные заказы и не должны раскрывать приватные поля.

### 18.1.1. CORS

REST API должен поддерживать CORS для frontend-приложения.

Разрешённые origins задавать только через ENV:

```yaml
app:
  cors:
    allowed-origins: ${CORS_ALLOWED_ORIGINS:http://localhost:3000,http://localhost:5173}
```

Не использовать `*` для production.

### 18.1.2. Rate limiting

Для защиты от brute-force и spam добавить rate limiting.

MVP-минимум:

- `/api/v1/auth/login`: ограничение по IP + email;
- `/api/v1/auth/register`: ограничение по IP;
- `/api/v1/auth/request-phone-otp`: ограничение по телефону + IP;
- `/api/v1/chats/*/messages`: мягкое ограничение частоты сообщений;
- `/api/v1/tasks`: ограничение на массовое создание заказов.

Реализация MVP:

- можно начать с Bucket4j или простого in-memory limiter;
- для production позже заменить на Redis-backed limiter или gateway-level protection.

### 18.2. JWT

Использовать:

- access token;
- refresh token.

Access token:

- короткий срок жизни;
- содержит userId и roles;
- не хранится в БД.

Refresh token:

- хранится в БД только как hash;
- может быть отозван;
- имеет срок жизни;
- связан с userAgent и ipAddress.

### 18.3. SMS/OTP и email verification

Phone verification Level 1 требует OTP.

В MVP не привязывать домен к конкретному SMS-провайдеру. Создать интерфейс:

```text
OtpService
SmsProvider
EmailVerificationService
```

Реализации:

```text
LogOnlySmsProvider для dev/test
ExternalSmsProvider для production
```

Конфигурация:

```yaml
app:
  otp:
    ttl: ${OTP_TTL:5m}
    max-attempts: ${OTP_MAX_ATTEMPTS:5}
    resend-cooldown: ${OTP_RESEND_COOLDOWN:60s}
  sms:
    provider: ${SMS_PROVIDER:log-only}
```

Email verification в MVP может быть включена или отключена через config flag:

```yaml
app:
  email-verification:
    enabled: ${EMAIL_VERIFICATION_ENABLED:false}
```

Если включена, использовать endpoints:

```http
GET  /api/v1/auth/verify-email?token={token}
POST /api/v1/auth/resend-verification
```

### 18.4. Пароли

### 18.5. Ownership checks

## 19. Payments

### 19.1. MVP-решение

MVP допускает два режима:

```text
OFF_PLATFORM
ON_PLATFORM_ESCROW
```

Но `ON_PLATFORM_ESCROW` можно подключать постепенно.

### 19.2. OFF_PLATFORM

Для части категорий разрешена оплата напрямую между заказчиком и исполнителем.

Но:

- платформа предупреждает о рисках;
- сделка всё равно фиксируется;
- чат, приёмка и отзывы остаются внутри платформы;
- рейтинг начисляется только если сделка была завершена в платформе.

### 19.3. ON_PLATFORM_ESCROW

Защищённая сделка через PSP.

Платформа не должна сама становиться банком или хранить деньги на собственном балансе без лицензии.

Использовать PSP, который поддерживает:

- приём платежей;
- удержание/резерв;
- выплаты исполнителям;
- возвраты;
- webhooks;
- KYC/KYB, если доступно.

### 19.4. PaymentTransaction

Создать entity `PaymentTransaction`. Поля сущности описаны в разделе 16.23.

Statuses:

```text
CREATED
PENDING
AUTHORIZED
HELD
CAPTURED
RELEASED
REFUNDED
PARTIALLY_REFUNDED
FAILED
CANCELED
```

### 25.4. Scheduled jobs и background processing

Для MVP нужны простые scheduled jobs:

### Antifraud processing

Антифрод в чате должен работать синхронно при сохранении сообщения:

1. пользователь отправляет сообщение;
2. backend проверяет текст регулярными правилами;
3. сообщение сохраняется;
4. если найден риск — создаётся RiskEvent;
5. пользователю показывается мягкое предупреждение;
6. при высоком риске создаётся ModerationCase.

## 31. Дополнительные критические требования для полной разработки

Этот раздел добавлен после повторной архитектурной проверки. Он закрывает не бизнес-функции, а production-ready слой: стабильность, безопасность, сопровождение, CI/CD, наблюдаемость и управляемую разработку через Codex.

### 31.1. State machine для Task / Offer / Deal / Milestone / Payment / Dispute

Codex не должен менять статусы хаотично. Для каждой ключевой сущности нужна явная state-machine.

#### TaskStatus transitions

```text
DRAFT -> MODERATION
DRAFT -> OPEN
MODERATION -> OPEN
MODERATION -> REJECTED_BY_MODERATION
OPEN -> IN_PROGRESS
OPEN -> CANCELED
OPEN -> EXPIRED
IN_PROGRESS -> WORK_SUBMITTED
IN_PROGRESS -> CANCELED только через dispute/admin decision
WORK_SUBMITTED -> COMPLETED
WORK_SUBMITTED -> REVISION_REQUESTED
WORK_SUBMITTED -> DISPUTED
REVISION_REQUESTED -> IN_PROGRESS
DISPUTED -> COMPLETED
DISPUTED -> CANCELED
```

Запрещено:

```text
COMPLETED -> IN_PROGRESS
CANCELED -> OPEN без отдельного clone/repost flow
EXPIRED -> IN_PROGRESS
```

#### TaskOfferStatus transitions

```text
PENDING -> ACCEPTED
PENDING -> REJECTED
PENDING -> CANCELED
PENDING -> EXPIRED
ACCEPTED -> нельзя менять без отмены сделки админом
```

#### DealStatus transitions

```text
ACTIVE -> WORK_SUBMITTED
WORK_SUBMITTED -> REVISION_REQUESTED
WORK_SUBMITTED -> COMPLETED
WORK_SUBMITTED -> DISPUTED
REVISION_REQUESTED -> ACTIVE
DISPUTED -> COMPLETED
DISPUTED -> CANCELED
ACTIVE -> CANCELED только через business rule/admin/dispute
```

#### MilestoneStatus transitions

```text
PENDING -> IN_PROGRESS
IN_PROGRESS -> SUBMITTED
SUBMITTED -> ACCEPTED
SUBMITTED -> REJECTED
REJECTED -> IN_PROGRESS
SUBMITTED -> DISPUTED
DISPUTED -> ACCEPTED
DISPUTED -> CANCELED
IN_PROGRESS -> CANCELED
PENDING -> CANCELED
```

Правила:

- `ACCEPTED` milestone нельзя вернуть в `IN_PROGRESS` без admin/dispute flow;
- если сделка `COMPLETED`, все обязательные milestones должны быть `ACCEPTED`;
- если milestone `DISPUTED`, сделка не может быть завершена обычной кнопкой `accept-work`;
- `REJECTED -> IN_PROGRESS` означает доработку этапа.

#### PaymentStatus transitions

```text
NOT_REQUIRED
PENDING -> AUTHORIZED
AUTHORIZED -> HELD
HELD -> RELEASED
HELD -> REFUNDED
HELD -> PARTIALLY_REFUNDED
PENDING -> FAILED
AUTHORIZED -> CANCELED
```

Требование к реализации:

- создать отдельные service methods для переходов статусов;
- не менять статус напрямую из контроллера;
- на invalid transition бросать `InvalidStatusTransitionException`;
- покрыть state-machine unit tests.

### 31.2. Конкурентность, атомарность и защита от race conditions

Критические операции должны быть атомарными:

- принятие отклика;
- создание Deal после принятия отклика;
- создание Chat после Deal;
- принятие работы;
- открытие спора;
- refresh token rotation;
- обработка payment webhook.

Требования:

- использовать `@Transactional` на write-сервисах;
- добавить `@Version` optimistic locking в ключевые Entity: `Task`, `TaskOffer`, `Deal`, `PaymentTransaction`, `DisputeCase`;
- для принятия отклика использовать блокировку или атомарную проверку статуса;
- не допускать ситуацию, когда заказчик принимает два отклика одновременно;
- добавить unique constraint: один активный chat/deal на один accepted offer;
- добавить integration test на параллельное принятие двух откликов.

### 31.3. Idempotency для критических POST-запросов

Для повторных запросов frontend/mobile и webhooks нужна idempotency.

Добавить заголовок:

```http
Idempotency-Key: <uuid-or-ulid>
```

Обязателен для:

- `POST /api/v1/tasks`;
- `POST /api/v1/tasks/{taskId}/offers`;
- `POST /api/v1/tasks/{taskId}/offers/{offerId}/accept`;
- `POST /api/v1/chats/{chatId}/submit-work`;
- `POST /api/v1/chats/{chatId}/accept-work`;
- payment webhook endpoints;
- refund/release payment operations.

Каноническая сущность `IdempotencyKey` описана в разделе 16.32.

Правило:

- одинаковый ключ + одинаковый requestHash возвращает тот же результат;
- одинаковый ключ + другой requestHash возвращает ошибку `IDEMPOTENCY_KEY_CONFLICT`.

### 31.4. Domain Events и Outbox Pattern

Нельзя отправлять уведомления, email, SMS или payment-side effects прямо внутри бизнес-транзакции без контроля.

Добавить `DomainEvent` как доменное событие в коде и `OutboxEvent` как persistable entity. Каноническая сущность `OutboxEvent` описана в разделе 16.33.

Event types:

```text
USER_REGISTERED
TASK_CREATED
TASK_PUBLISHED
OFFER_CREATED
OFFER_ACCEPTED
DEAL_CREATED
CHAT_MESSAGE_CREATED
WORK_SUBMITTED
WORK_ACCEPTED
REVISION_REQUESTED
DISPUTE_OPENED
DISPUTE_RESOLVED
FEEDBACK_CREATED
VERIFICATION_APPROVED
PAYMENT_HELD
PAYMENT_RELEASED
PAYMENT_REFUNDED
```

MVP:

- сохранять outbox events в БД;
- scheduled job обрабатывает pending events;
- уведомления строятся из outbox;
- позже можно заменить на Kafka/RabbitMQ без изменения домена.

### 31.5. Observability: логирование, метрики, health checks

Добавить Spring Boot Actuator.

Endpoints:

```text
/actuator/health
/actuator/info
/actuator/metrics
```

Production:

- `/actuator/health` можно открыть ограниченно;
- остальные endpoints закрыть admin/internal access.

Логи:

- JSON logs в production;
- correlationId/requestId для каждого запроса;
- userId в логах только если безопасно;
- не логировать JWT, refresh token, password, документы, ИИН, номера карт.

Метрики:

- число регистраций;
- число созданных заказов;
- число откликов;
- offer acceptance rate;
- chat messages count;
- work submitted count;
- disputes count;
- verification pending count;
- login failures;
- API latency;
- DB query latency;
- failed payment webhooks.

### 31.6. Backup / Restore / Disaster Recovery

Для production нельзя ограничиваться Docker volume.

Требования:

- ежедневный backup PostgreSQL;
- отдельный backup object storage metadata и файлов;
- проверка restore минимум раз в месяц;
- хранить backup отдельно от основного сервера;
- шифровать backup;
- документировать процедуру восстановления.

RPO/RTO для старта:

```text
RPO: до 24 часов
RTO: до 8 часов
```

Для платежей и документов верификации RPO должен быть строже, если появится полноценная on-platform payment модель.

### 31.7. Data privacy, retention и удаление данных

Нужно добавить отдельную политику хранения данных.

Минимальные правила:

- удаление пользователя — soft delete;
- документы верификации не должны храниться бесконечно;
- документы rejected verification удалять/архивировать через настраиваемый срок;
- chat messages и deal history хранить для споров и аудита;
- пользователь может запросить удаление аккаунта;
- нельзя удалять финансовые/audit данные, если они нужны по закону или для спора;
- персональные данные должны быть минимальными: не собирать ИИН/документы, пока они не нужны для конкретного уровня верификации.

Каноническая сущность/config `DataRetentionPolicy` описана в разделе 16.34.

### 31.8. Безопасность файлов

Для вложений и документов добавить правила:

- whitelist MIME types;
- max file size по типу файла;
- запрет исполняемых файлов;
- проверка расширения и MIME независимо;
- антивирусная проверка через ClamAV или внешний сервис в future-ready архитектуре;
- EXIF-stripping для изображений, если фото публичное;
- private bucket для документов верификации;
- signed URL с коротким сроком жизни для private files;
- audit log на просмотр документов верификации админом.

MVP minimum:

```text
allowed image: jpg, jpeg, png, webp
allowed docs: pdf, jpg, png
max public image: 10 MB
max verification document: 20 MB
max chat file: 25 MB
```

### 31.9. API contract и версионирование

Все публичные API должны быть стабильными.

Требования:

- `/api/v1` сохраняется;
- breaking changes только через `/api/v2`;
- DTO нельзя менять хаотично после frontend integration;
- все endpoints документировать через OpenAPI;
- добавить OpenAPI generation в CI;
- добавить contract tests для критических endpoints.

### 31.10. Performance и scalability minimum

Codex должен учитывать производительность уже в MVP.

Требования:

- pagination обязателен для всех списков;
- max page size = 100;
- default page size = 20;
- не делать N+1 queries;
- использовать `@EntityGraph`, fetch join или DTO projections;
- индексы для всех фильтров;
- не грузить chat messages без pagination;
- не грузить attachment binary через backend без необходимости, использовать signed URLs.

Добавить нагрузочные smoke-тесты позже:

- 50 000 tasks;

### 31.11. Feature flags и platform settings

Не хардкодить бизнес-правила.

Добавить конфигурацию:

- включены ли payments;

### 31.12. Timezone, currency и округления

Первый рынок — Казахстан.

Правила:

Подключить позже, если реально используешь:

- **Linear/Jira** — если будешь вести задачи не в GitHub Issues;
- **Slack** — если будет команда и нужна коммуникация;
- **Google Drive** — если ТЗ/документы будут жить в Drive;
- **Figma** — когда появится frontend/UI design;
- **OpenAI Developer Docs / docs MCP**, если доступно в твоём Codex, для актуальных ссылок на документацию.

Не подключать лишнее на старте:

- Gmail;
- календарь;
- CRM;
- production database;
- production cloud account.

Причина: плагины расширяют доступ Codex к внешним данным и действиям. OpenAI docs указывают, что plugins могут включать skills, app integrations и MCP servers, а подключённые внешние сервисы остаются под своими правилами authentication/privacy/data sharing.

### 32.9. GitHub Actions CI

Создать `.github/workflows/ci.yml`:

```yaml
name: CI

on:
  pull_request:
  push:
    branches: [ main, develop ]

jobs:
  backend:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: '21'
          cache: maven
      - name: Build and test
        run: mvn -B clean verify
```

Позже добавить:

- OWASP Dependency Check или Snyk/GitHub Dependabot;
- Docker build;
- OpenAPI artifact;
- JaCoCo report;
- Liquibase validation.

### 32.12. Как делить работу между Codex-агентами

Можно запускать параллельно только независимые задачи:


Нельзя параллелить:

Потому что будут конфликты в Entity, migrations и security.

- не отдал ли Entity наружу из Controller;

- не добавил ли лишнюю зависимость;

## 34. Главный вывод

HandyNest должен быть не простой доской заказов, а полноценной платформой доверенных сделок.

Главные отличия от обычных конкурентов:

- чат является центром сделки;
- принятие работы происходит прямо из чата;
- есть сценарии принять / доработка / спор;
- контакты открываются контролируемо;
- есть верификация исполнителей по уровням;
- есть Top Performers;
- есть geo/radius/ETA;
- есть мягкая монетизация, которая не убивает рост;
- есть поддержка локальных и удалённых услуг;
- есть подготовка к оплатам, эскроу и B2B;
- backend строится как чистый modular monolith на Java 21 / Spring Boot 3.5.x.

Codex должен использовать этот документ как главный источник требований и выполнять разработку по фазам, сохраняя проект компилируемым после каждого этапа.
